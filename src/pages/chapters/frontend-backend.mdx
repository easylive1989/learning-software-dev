## 先想像一間餐廳

你走進一間餐廳。你看得到桌椅、菜單、服務生；你看不到廚房裡的爐火，也看不到後面倉庫裡堆了多少食材。可是你點的每一道菜，都要經過這三個地方才會出現在你面前。

一個網站或 App 也是這樣分工的：**前端是外場，後端是廚房，資料庫是倉庫。** 點下面任何一區，看它在軟體裡是誰；或按「看一道菜怎麼來」，跟著一張訂單走一圈。

<RestaurantMap client:visible />

注意那條虛線框：廚房和倉庫都在公司的伺服器上，你永遠看不到。你看得到的只有外場，而外場的程式碼其實是被下載到**你的**手機或電腦上執行的。

## 點菜單就是 API

外場和廚房之間靠點菜單溝通。在軟體裡，這張點菜單叫做 **API**：前端和後端事先約好「你要什麼就這樣寫，我會這樣回給你」。送出去的單子叫 request，端回來的菜叫 response。

## 動手試試：一次點擊背後發生了什麼

選一個動作，再選一個「今天的狀況」，按播放。每一步上面是餐廳裡發生的事，下面灰色的部分是工程師實際會看到的東西。

<RequestJourney client:visible />

幾個值得多玩一下的組合：

- **「廚房忙不過來」**：注意左邊的瀏覽器在等待時顯示「載入中」。等待的時候畫面要長什麼樣子、能不能讓使用者再按一次，這些都是前端要決定的事。
- **「倉庫打不開」與「點菜單寫錯了」**：兩個都失敗了，但回來的數字不一樣。`500` 開頭是 5，代表廚房（伺服器）那邊出事；`400`、`401` 開頭是 4，代表你送出去的單子本身有問題。光看這個數字，工程師就知道該先查誰。

## 為什麼這個分工很重要

因為前端的程式跑在使用者的裝置上，**使用者其實可以改它**。懂一點技術的人可以打開瀏覽器的開發者工具，把「數量最多 5 杯」的限制拿掉，或是直接繞過按鈕送出自己編的請求。

這就像客人可以在點菜單上亂寫。下面這支手機的 + 按鈕最多只能按到 5 杯，先正常點一次，再打開開發者工具把數量改掉，比較「只靠前端擋」和「後端也檢查」的差別。

<ForgedOrder client:visible />

所以真正的把關一定要在廚房：前端可以先擋一次讓使用者體驗好一點，**後端一定要再檢查一次**。這也是為什麼你會聽到工程師說「前端有擋，但後端也要驗」。

## 深入一點

<Deeper title="為什麼前端不能直接連資料庫？" forWhom="適合所有人">

如果外場可以直接走進倉庫，那每一位客人都可以。前端的程式碼會被下載到使用者的裝置，裡面的任何帳號密碼都等於公開。所以資料庫一定藏在後端後面，只有後端知道怎麼進去，而且後端會檢查每個請求有沒有權限。

</Deeper>

<Deeper title="畫面是誰畫的？SSR 與 CSR" forWhom="給後端工程師">

前面的餐廳比喻是「廚房只出菜（JSON），擺盤在外場（瀏覽器）完成」。這叫 **CSR（Client-Side Rendering）**，React、Vue 寫的單頁應用大多是這樣。

另一種做法是廚房連盤子都擺好才端出去：伺服器直接產生完整的 HTML。這叫 **SSR（Server-Side Rendering）**。好處是第一次打開比較快、搜尋引擎比較好讀；代價是伺服器要做更多事。

<PlatingDiagram />

現在的框架（Next.js、Nuxt、Astro）常常混用：第一次載入用 SSR，之後的互動交給瀏覽器。所以當前端工程師說「這頁要改成 SSR」，意思是「這頁的擺盤要搬回廚房做」，後端的負擔和快取策略都會跟著改變。

</Deeper>

<Deeper title="誰負責什麼：一張對照表" forWhom="給前端與後端工程師">

| 問題 | 通常是誰的事 | 為什麼 |
| --- | --- | --- |
| 按鈕按了沒反應 | 前端 | 點擊事件、畫面狀態都在瀏覽器裡 |
| 列表顯示的資料是錯的 | 先看 API 回應 | 回應錯就是後端，回應對就是前端 |
| 頁面很慢 | 兩邊都要查 | 可能是 API 慢、資料太大，也可能是前端畫太多東西 |
| 不該看到的資料被看到 | 後端 | 權限檢查必須在伺服器做 |
| 送出表單出現 400 | 先看前端送了什麼 | 4xx 代表請求內容不符合約定 |
| 偶爾出現 502、504 | 後端或維運 | 通常是伺服器本身或中間的閘道出問題 |

</Deeper>
