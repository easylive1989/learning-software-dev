## 快取是什麼

想像一間圖書館。最常被借的二十本書，館員不會每次都跑去地下書庫拿，而是放在櫃台旁的推車上。讀者一問，伸手就有。

**快取（cache）**就是那台推車：把常被問的答案先記在一個很快的地方，下次有人問就直接回答，不用再去資料庫慢慢查。

推車上的書也不能永遠放著，因為書庫裡的版本可能更新了。所以每本書都有一個「放多久就要收回去重拿」的期限，工程師叫它 **TTL（Time To Live）**。期限到了叫做**過期**，下一個來問的人就得跑一趟書庫。

快取讓資料庫很輕鬆。但也正因為資料庫平常很輕鬆，大家會忘記它其實撐不住全部的流量。一旦快取在錯的時間失效，事情就會很快變得很糟。接下來是工程師最常遇到的三種狀況，每一種都先看問題，再看解法。

## 問題一：快取雪崩

**大量快取在同一時間過期**，所有請求一起湧進資料庫。

最常見的原因很平凡：系統在某個時間點一口氣把所有資料寫進快取，而且用了同一個 TTL。它們同時被寫進去，也就會同時過期。快取伺服器重開機、整個清空，也會造成一樣的結果。

先看問題，再切到解法比較：

<CacheStory client:visible sceneIds={['avalanche', 'jitter']} />

**解法的關鍵是「錯開」。** 在 TTL 上加一段隨機時間，工程師稱為加 jitter，讓過期時間分散開來。其他常見做法：

- **預熱（warm up）**：快取重開機後，先把熱門資料載入，再讓流量進來。
- **限流與降級**：資料庫快撐不住時，主動擋掉一部分請求，或回傳簡化版的內容，至少讓網站不要整個掛掉。
- **多層快取**：一層失效，還有另一層頂著。

## 問題二：快取擊穿

雪崩是很多 key 一起過期；**擊穿是一個非常熱門的 key 過期**。

例如限時特賣的商品頁，八成的人都在看它。它的快取一過期，在新答案放回快取之前的那一兩秒內，所有人都會去資料庫查同一筆資料。如果那筆資料剛好又很難算，一個 key 就足以打垮資料庫。

<CacheStory client:visible sceneIds={['breakdown', 'lock']} />

**解法的關鍵是「只派一個人去拿」。** 同一個 key 同一時間只允許一個請求去資料庫，其他人等它把答案放回快取。工程師會說「加鎖（mutex）」或「single flight」。其他常見做法：

- **熱門資料不設過期**，改由背景程式定時更新，使用者永遠不會遇到「剛好過期」的那一刻。
- **提前更新**：快過期前，就先在背景把新資料準備好。

## 問題三：快取穿透

前兩個問題的資料都存在，只是快取剛好沒有。**穿透是請求的資料根本不存在。**

有人（可能是攻擊，也可能是程式寫錯）大量查詢不存在的商品。快取裡沒有，資料庫裡也沒有，因為答案是「沒有」，所以永遠不會被放進快取。每一次都會穿過快取打到資料庫。

<CacheStory client:visible sceneIds={['penetration', 'guard']} />

**解法的關鍵是「在門口就擋掉」。** 常見做法：

- **把「查無資料」也記進快取**，給一個短的 TTL。下次同樣的查詢，快取直接回答「沒有」。
- **Bloom filter**：一種很省空間的名冊，可以快速判斷「這個 id 一定不存在」，直接擋掉。
- **檢查輸入**：商品編號明顯不合理（負數、格式不對）的請求，在最前面就拒絕。

## 三個問題放在一起看

| | 雪崩 | 擊穿 | 穿透 |
| --- | --- | --- | --- |
| 發生什麼 | 大量 key 同時過期 | 一個熱門 key 過期 | 查詢不存在的資料 |
| 資料存在嗎 | 存在 | 存在 | 不存在 |
| 一句話解法 | 把過期時間錯開 | 只派一個人去拿 | 在門口就擋掉 |
| 工程師關鍵字 | TTL jitter、預熱、限流 | mutex、single flight、永不過期 | 快取空值、Bloom filter |

## 深入一點

<Deeper title="為什麼「重開資料庫」常常沒用？" forWhom="給前端工程師">

在雪崩的動畫裡，資料庫倒下後，快取裡依然什麼都沒有。如果這時候直接把資料庫重開，所有請求會在第一秒全部湧回來，資料庫會再倒一次。

所以真實的事故處理順序通常是：先在入口限流（只放一小部分請求進來）→ 讓資料庫和快取慢慢恢復 → 逐步放寬限流。這也是為什麼工程師在事故時會說「先止血」。

</Deeper>

<Deeper title="快取最難的其實是「資料不一致」" forWhom="給前端與後端工程師">

快取裡的答案是過去某個時間點的複本。資料庫更新了，快取還沒過期，使用者就會看到舊資料。例如改了商品價格，頁面上卻還是舊價錢。

常見的策略是更新資料庫後，主動把對應的快取刪掉，下一次讀取時再重新載入（cache aside）。但在高併發下，「刪快取」和「讀舊資料寫回快取」的順序可能交錯，所以有些系統會延遲再刪一次。

對前端工程師來說，這解釋了為什麼後端有時會說「資料要等幾秒才會更新」：那幾秒通常就是快取的 TTL。

</Deeper>

<Deeper title="快取不只在後端" forWhom="給後端工程師">

瀏覽器本身也有快取（HTTP cache），CDN 也是一層快取。前端工程師在意的 `Cache-Control`、檔名加 hash、Service Worker，都是同一個概念的不同層次。當後端改了 API 的快取標頭，前端看到的行為也會跟著改變。

</Deeper>
